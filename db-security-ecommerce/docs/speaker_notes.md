**understand** the result, not that nothing ever goes wrong.

### Slide 2: Today's journey: six parts in about 50 minutes  _(≈ 1 min)_

## 1 · Key concepts

### Slide 3: Key concepts from Chapter 2  _(≈ 0.5 min)_

Part one: the key concepts. I will go through the chapter in the same order as the lecture: access control, authentication and passwords, MFA, roles and attributes, secure coding, and encryption.

For each idea I will also say where you will see it later in my project.

### Slide 4: Access control: who may see, query, modify or execute what  _(≈ 1.5 min)_

Access control decides what an already-authenticated user is allowed to do in the database.

There are four common models. In RBAC, rights belong to job roles, like "sales", not to individual people. In DAC, the owner of the data decides who gets access. In MAC, a central authority gives security labels that users cannot change, like in the military. In ABAC, the decision depends on attributes: the user's department, the location, the time, or properties of the data itself.

In my project I implemented RBAC and ABAC, and you will see both in the demo. DAC and MAC I only explain.

### Slide 5: Authentication first, then authorization  _(≈ 1.5 min)_

These two words sound similar but they answer different questions.

Authentication asks "who are you?". It is like showing your passport at the airport security check. It always happens first.

Authorization asks "what are you allowed to do?". It is like the boarding pass that lets you sit only in your own seat.

In ShopDB, authentication is the login procedure with the password check, lockout and optional MFA. Authorization is the roles, the GRANT and DENY permissions, and the row-level rules.

### Slide 6: Authentication methods: what can prove who you are?  _(≈ 1.5 min)_

The lecture lists six families of authentication methods.

Something you KNOW, like a password or PIN. Something you HAVE, like a phone with an authenticator app or a security key. Something you ARE, like a fingerprint or your face. SOMEWHERE you are, like an allowed IP address. ADAPTIVE methods look at the risk, for example a new device or a login at 3 a.m. And FEDERATED login lets a trusted third party like Google or Microsoft confirm your identity.

My project combines the first two: a password you know, plus a one-time code from your phone.

### Slide 7: Password policy: length beats complexity  _(≈ 1.5 min)_

Passwords are still the first line of defence, and weak or reused passwords are a top cause of breaches.

A good policy has these elements: a minimum length, a mix of character types, a blocklist of common passwords, lockout after repeated failures, password history so old passwords cannot be reused, and safe storage. Storage means never plaintext: we store a random salt and a slow hash.

On the right you see why length matters. The number of possible passwords is C to the power N: C is the size of the character set and N is the length. Six lower-case letters give about 300 million options, which a computer tries in seconds. My policy needs at least 10 characters from all four groups. That gives up to 94 to the power 10: about 54 billion billion options.

### Slide 8: How passwords are attacked, and what stops each attack  _(≈ 1.5 min)_

Passwords are attacked in many ways: disclosure, guessing, snooping with key loggers, and automated cracking.

The lecture names three cracking types. A dictionary attack tries every word in a list. My blocklist rejects the most common passwords. A hybrid attack adds numbers and symbols, like "Password123!". The complexity rules plus the blocklist stop that. A brute-force attack tries every combination. Against that, lockout stops online guessing after five tries, and the slow salted hash makes offline guessing very expensive.

The salt is a random value per user, so two users with the same password still get different hashes, and pre-computed "rainbow tables" are useless.

### Slide 9: MFA: one stolen password is not enough  _(≈ 1.5 min)_

Multi-factor authentication combines two or more DIFFERENT types of proof. The timeline shows the evolution: single factor is a password only, two-factor adds a device or a biometric, and full MFA can combine all three.

The big advantage: even if an attacker steals the password, they still need my phone. The disadvantages are a slower login, more setup, and a problem if you lose your phone.

In my project, after the password is correct, the user types a six-digit code from Google Authenticator. The code changes every 30 seconds and is computed from a shared secret plus the current time. That standard is called TOTP.

### Slide 10: Role- and attribute-based privileges: the building blocks  _(≈ 1.5 min)_

The lecture describes four basic elements. USERS are the accounts that connect. AUTHENTICATION verifies them. ROLES group privileges together. PRIVILEGES are the actual rights, like SELECT, INSERT, UPDATE, DELETE or EXECUTE.

The key principle is least privilege: give only what the job needs.

RBAC stops at the table level: "sales may read Orders". ABAC adds a rule about each row: "and only orders from my own region". I will show exactly this in the demo.

### Slide 11: Query hardening: data must never become code  _(≈ 2 min)_

Secure coding means building security into the database code from the start. The lecture calls this the secure development life cycle. Fixing problems after deployment can cost up to 100 times more.

The most famous problem is SQL injection. On the left, the program glues the user's input into the SQL text. The input contains a quote and OR 1=1, so the WHERE clause is always true and the attacker logs in without a password.

On the right, the same input is sent as a PARAMETER. SQL Server compiles the query first and only then plugs in the value, so the quote is just a character in a username that does not exist.

The other principles on the left of the slide: defence in depth, fail securely, least privilege, input validation, no secrets in code, and error messages that do not leak details.

### Slide 12: Encryption & data protection: protect data in every state  _(≈ 2 min)_

Encryption is a layered defence. Data has three states. AT REST means stored on disk or in a backup. IN MOTION means travelling over the network. IN USE means being processed and shown to users.

Each state has its own tool. TDE encrypts the database files and backups. TLS encrypts the connection. Dynamic data masking hides parts of values like e-mail addresses from people who do not need them.

The lecture also shows column-level encryption for very sensitive fields like card numbers, and Always Encrypted, where even the DBA cannot read the data because the keys stay in the client application.

Finally, data classification: you label sensitive columns so that you know what to protect. I implemented TDE, column encryption, masking and classification, and my app uses an encrypted connection.

## 2 · Why it matters

### Slide 13: Why it matters for an online shop  _(≈ 0.3 min)_

Part two: why does this matter in the real world, especially for an online shop?

### Slide 14: An online shop is a target: money, personal data and trust  _(≈ 2 min)_

An online shop stores exactly what attackers want: customers' personal data, payment data and money flows.

Injection is still in the OWASP Top 10 list of the most critical web application risks; in the 2021 edition it is number three. The lecture reminds us that fixing a vulnerability after deployment can cost up to 100 times more than during development.

Card payments come with the PCI DSS standard, which requires stored card numbers to be unreadable, for example encrypted. And privacy laws such as the EU's GDPR, and Ethiopia's own personal data protection law from 2024, make companies responsible for protecting customer data.

For a shop in Addis Ababa, a breach means fraud, lost customers and legal problems.

### Slide 15: Risk identification checklist: 10 digital assets of ShopDB  _(≈ 2 min)_

Before building anything I made a risk checklist, using the form from the assignment.

For each digital asset I wrote the threat, the weakness that allows it, and how likely and how harmful it is. Likelihood times impact, each from 1 to 3, gives the rating: 9 is critical, 6 is high.

Two risks are critical: weak passwords and SQL injection, so I fixed those first and I demonstrate them first. Every row has a control, and the last column shows which script implements it. So this table is also the map of my whole project.

## 3 · Implementation approach

### Slide 16: How I built it  _(≈ 0.3 min)_

Part three: my implementation approach. As the assignment asks, I show it with diagrams, not with code.

### Slide 17: Architecture: two doors into the same database  _(≈ 2 min)_

This is the architecture. A browser talks to a small Flask web application. It runs only on 127.0.0.1, so nobody else on the network can reach it.

The app has two "doors" into SQL Server. The green door is the hardened path: it connects as shop_app, a login that is only allowed to EXECUTE the stored procedures in the "app" schema. It cannot read any table directly.

The red door is the deliberately vulnerable path for the demo only. It glues input into SQL strings and connects as legacy_app, which can read and write every table, like many badly built real applications.

Inside SQL Server the tables live in the dbo schema, the procedures in the app schema, and the row-level security rules in the sec schema. On disk everything is encrypted with TDE. The passwords for all of this are in a .env file, never in the code.

### Slide 18: Build order: one script per security layer  _(≈ 1 min)_

I built the project in layers, one numbered script per layer, and each script can be run again safely.

Script 1 creates the database with all constraints and sample data. Script 2 adds the password policy. Script 3 adds role-based access control, and script 4 adds attribute-based control with row-level security and masking. Script 5 contains the hardened stored procedures against SQL injection. Script 6 adds encryption: TDE, column encryption and data classification, and 6b is a disaster drill for a lost certificate. Script 7 adds MFA.

A runner script reads the passwords from the .env file, so no password is written in any SQL file. Building everything from zero takes about 10 seconds.

### Slide 19: Data model: 8 tables protected by constraints  _(≈ 1.5 min)_

This is the data model. Customers place Orders; each order has OrderItems that point to Products, and one Payment. Users are the website accounts; each one belongs either to a customer or to a staff member. The Staff table also stores the attributes I use for ABAC: department and region. Every important action is written to the AuditLog.

Constraints are the first security layer: the database itself refuses bad data, even if the application has a bug. Primary and foreign keys, UNIQUE for e-mails and usernames, CHECK for prices, phone format and allowed characters in usernames, DEFAULT values, and NOT NULL.

Passwords are stored as a random salt plus a hash repeated 5,000 times, and the card number column is encrypted later by script 6.

### Slide 20: The hardened login, step by step  _(≈ 1.5 min)_

This flowchart shows what happens when someone logs in through the hardened path.

First the input is validated: a username may only contain letters, digits, dot and underscore. Then the user is looked up with a parameter, never by building SQL text. If the account is locked, we stop. Then the password is hashed with the user's own salt and compared.

A wrong password increases the failed-attempts counter, and at five the account is locked for 15 minutes. The message is always the same, "invalid username or password", so an attacker cannot learn which usernames exist.

If the password is right and MFA is on, the user must also type the code from the phone. Only then the session starts, and the app stores the customer ID in SESSION_CONTEXT, which row-level security uses later. Every step is written to the audit log.

### Slide 21: Access design: roles pick tables, attributes pick rows  _(≈ 1.5 min)_

On the left are my five roles and the website login. Each role gets only what the job needs. Admin manages the shop but is NOT a database owner: it cannot drop tables, cannot read password hashes, and cannot delete the audit log. The website login can only execute procedures.

On the right is the ABAC part. The same SELECT on the Orders table returns a different number of rows depending on the user's attributes. Admin, auditor and support, whose region is ALL, see all 10 orders. Abebe in sales, region Addis Ababa, sees 4. Hana in Hawassa sees 3. These are the real numbers from my test.

I also used dynamic data masking: support staff see e-mails like s-X-X-X at X-X-X-X dot com, while sales see the real address because they need to contact customers.

### Slide 22: Encryption design: a chain of keys  _(≈ 1.5 min)_

Encryption is only as safe as its keys, so I designed two key chains.

On the left is TDE. The service master key protects the master key of the server, which protects my certificate, which protects the database encryption key, which encrypts every page written to disk, including the backups.

On the right is column encryption for card numbers. Inside ShopDB, a certificate protects a symmetric AES-256 key, and only the admin role is allowed to use it. Sales can select the column but gets binary data or NULL.

The most important lesson: I backed up the TDE certificate and its private key to files with a password. Without them, an encrypted backup can never be restored, not even by me. My drill script proves this.

Part four: the results. I will now switch to the live demonstration. If anything fails, the next slides show the same results as screenshots from my test runs.

### Slide 24: Demo plan (about 10 minutes)  _(≈ 10 min)_

Here is the order of my demo, so you can follow along.

First I attack the vulnerable login and search with SQL injection, and then I try exactly the same input on the hardened version. Second, the lockout and the MFA login. Third, I switch to SQL Server Management Studio and run the same query as different users, to show RBAC, row-level security and masking. ### Slide 25: Result 1: the same input, two different outcomes  _(≈ 0.75 min)_

Result one. On the left, I typed quote OR 1=1 dash dash into the vulnerable login. You can see the SQL that the app built: the WHERE clause became always true, and I am logged in as Selam without knowing her password.

On the right, exactly the same input in the hardened login: "Invalid username or password". The stored procedure received it as a parameter, so it was just a strange username. It was also rejected by input validation and written to the audit log.

### Slide 26: Result 2: data theft and price fraud, blocked  _(≈ 0.75 min)_

Result two: the search box. With a UNION injection the vulnerable search returns every username together with its password hash. Thanks to the salt and the 5,000 rounds these are hard to crack, but they should never leak.

A second payload, a stacked UPDATE, changed the laptop price to 1 birr. That is real fraud.

On the hardened side the same inputs return nothing, and the parameters are shown separately from the SQL text. The website login has no right to read tables anyway, so even a mistake in the code would fail.

### Slide 27: Result 3: least privilege, proven for every role  _(≈ 0.75 min)_

Result three is the permission matrix. My script logs in as each user with EXECUTE AS, tries ten actions, and records whether SQL Server allowed or denied it. Everything is inside a transaction that is rolled back, so nothing changes.

Look at the website_app column: it is denied on every table, and only allowed to execute the app procedures. Nobody can read password hashes or delete the audit log, not even admin. Only the deliberately bad legacy login on the right can do the dangerous things, and that is exactly why injection on the red door was so damaging.

### Slide 28: Result 4: same query, different rows and columns  _(≈ 0.75 min)_

Result four is ABAC. This is real output: one SELECT on Orders, run as five users. Admin, auditor and support see all ten, Abebe in Addis sees four, Hana in Hawassa sees three.

Below, the same SELECT on Customers: Abebe sees only Addis customers with real e-mail and phone. Dawit from support sees all customers, but masked.

On the right you see why this is attribute-based and not role-based: when I moved Abebe to Hawassa I only changed his Region attribute, not his role, and he immediately saw the Hawassa orders. When I set IsActive to zero, he saw nothing.

### Slide 29: Result 5: encrypted at rest, and the certificate really matters  _(≈ 0.75 min)_

Result five is TDE. The top-left shows the encryption state 3, which means encrypted, with AES-256 protected by my certificate. SQL Server also encrypts tempdb automatically.

Below it is the proof: I searched the backup files for a product code and a test card number. In the backup taken BEFORE TDE, both were found as readable text. In the backup taken AFTER TDE, nothing was found.

On the right is my disaster drill. Without the certificate, restoring the encrypted backup fails with error 33111, "cannot find server certificate". After restoring the certificate from my backup files, the restore works and all data is there.

### Slide 30: Result 6: card numbers and MFA  _(≈ 0.75 min)_

Result six. On the left, card numbers. The admin role holds the key permission and sees the real numbers; I used official test card numbers, not real cards. Sales can select the same column, but decryption returns NULL, and trying to open the key gives "cannot find the symmetric key".

On the right is MFA. The user scans the QR code with Google Authenticator. After that, the password alone is not enough: the app asks for the six-digit code. A wrong code is rejected and counts towards the lockout.

### Slide 31: Verified, not assumed  _(≈ 1 min)_

To be sure that everything really works, and not only on my screen, I wrote an automated smoke test. It uses the running website like a browser and checks 22 security behaviours: injection, lockout, row-level security, CSRF protection, the password policy and MFA. All 22 pass.

All eight SQL scripts can be re-run safely and rebuild everything from zero in about ten seconds. All ten risks from my checklist are mapped to a control. And there is no password in any source file: everything is in the .env file, which is never committed.

## 5 · Conclusion & feedback

### Slide 32: Conclusion: no single control is enough, so I built layers  _(≈ 2 min)_

My conclusion: database security is not one feature, it is layers. If one layer fails, the next one still protects the data.

The network layer: the app only listens on this computer and uses an encrypted connection. Authentication: strong passwords, lockout and MFA. Authorization: roles, row-level rules and masking. Query hardening: stored procedures and parameters. Data protection: TDE, column encryption and classification. And monitoring: the audit log records everything.

I also want to be honest about the limits. SQL Server has no feature called ABAC, so I built it from row-level security and attributes. SQL logins have no MFA, so MFA lives in the app. In production I would hash passwords with bcrypt or Argon2, and use Always Encrypted so that even the DBA cannot read card numbers.
